# qcheck — DECISIONS.md

> 「なぜAではなくBか」を記録する。コードからは読めない判断根拠。
> PROGRESS.mdの決定ログは「何をしたか」の実行記録、本ファイルは「なぜそうしたか」の判断根拠。

| Phase | 大分類 | 小分類 | 選択 | 却下案 | 理由 |
|-------|--------|--------|------|--------|------|
| 0.1.0 | 実行方式 | LLM呼出 | Agent ツール（サブエージェント） | API直叩き / `uv run qcheck` 等のCLI | Maxプラン内で完結、API課金不要、CLI起動オーバーヘッドなし。dot_claudeのスキル文化とも整合 |
| 0.1.0 | スコープ | 機能境界 | runner 限定 | runner + generate（VISION走査で自動作成） | 観点の妥当性は対話で詰める方が品質高い。自動生成は誤判定/ノイズの量産源 |
| 0.1.0 | 配置 | qcheck.md 置き場所 | `tests/` 直下 | `qchecks/` 等の専用dir / コード隣接 | unit test と同居でテスト類の発見性向上。ディレクトリ規約を増やさない |
| 0.1.0 | 判定回数 | リトライ戦略 | 1回判定 | 多数決（3回中2回pass）/ 再判定ループ | advisory扱いで厳格な再現性は不要。コストと時間を最小化 |
| 0.1.0 | 結果出力 | 履歴管理 | `tests/qcheck_result.YYMMDD.md` 日付別 | 元 qcheck.md のチェックボックス上書き | 元ファイルを書き換えると履歴が消える。日付別ログで品質変化の経時追跡が可能 |
| 0.1.0 | CI連携 | 失敗時の扱い | テスト失敗にしない（advisory） | pytest内 fail / CI gate化 | AI判定の非決定性による flaky test を回避。人間レビュー前提 |
| 0.1.0 | 起動条件 | 空振り防止 | qcheck.md 存在時のみ起動 | 常時起動、不在なら no-op | 不在時は新規作成フロー（対話）に自然誘導したい |
| 0.1.0 | pj管理 | 設計記録の重さ | VISION/DECISIONS/PROGRESS 3点セット | SKILL.md単体（既存skill慣習） | 実装はまだなく開発を引き継げる粒度の記録が必要。「独立pj」位置付けに従う |
